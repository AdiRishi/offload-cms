---
title: Add customer accounts
description: Let site visitors sign up, log in, reset their password, and see their own documents, through a second auth collection next to the admin's users.
---

This guide adds a `customers` collection whose users log in to the site but never to the admin. Visitors sign up with an email and a password, confirm the email, log in, reset a forgotten password, and reach pages that only a logged-in customer sees. `@adirishi/offload-accounts` holds the logic. The forms come from Offload's shadcn registry, and the site writes its own routes and server functions.

The site needs:

- The setup from [Getting started](/getting-started).
- The Workers Paid plan. [Accounts need the Workers Paid plan](#accounts-need-the-workers-paid-plan) explains why.
- An email adapter, such as the one in [Send email with Cloudflare Email Service](/email). Payload sends the verification and password reset emails through it.
- Tailwind CSS v4, shadcn with `"rsc": true`, and the `@offload` registry in `components.json`. The steps "Set up Tailwind and shadcn" and "Add Offload's registry" in [Take form submissions](/forms) set them up.

<Steps>
  <Step title="Install the packages">
    ```json package.json
    "@adirishi/offload-accounts": "{{version}}",
    "@adirishi/offload-tanstack": "{{version}}",
    "zod": "^4.0.0"
    ```

    The site already has `@adirishi/offload-cloudflare`, which the package uses for `verifyTurnstile()`. Install `@adirishi/offload-accounts` before you add the registry components. The registry doesn't list the package, so the shadcn CLI never installs it or changes its version.

  </Step>
  <Step title="Add the bindings">
    Add a Rate Limiting binding for logins and password reset requests, and the site's public origin, to every Wrangler environment:

    ```jsonc wrangler.jsonc
    "vars": { "SITE_URL": "https://example.com" },
    "ratelimits": [
      { "name": "ACCOUNTS", "namespace_id": "1002", "simple": { "limit": 10, "period": 60 } }
    ]
    ```

    The limit applies to each key on its own. This binding allows ten login attempts a minute from one IP, and ten password reset requests a minute from one IP or for one email. Visitors behind one shared address, such as an office network or a mobile carrier's NAT, share an IP's allowance, so don't set it much lower. `period` must be `10` or `60`. The links in account emails start with `SITE_URL`, so give each environment its own, such as `http://localhost:4173` for `vite preview`.

    Put the Turnstile secret key in `.dev.vars`. For local runs, use Cloudflare's testing secret, which passes every token:

    ```ini .dev.vars
    TURNSTILE_SECRET_KEY=1x0000000000000000000000000000000AA
    ```

    Then run `pnpm wrangler types`, so `env.ACCOUNTS`, `env.SITE_URL`, and `env.TURNSTILE_SECRET_KEY` have types.

  </Step>
  <Step title="Create the customers collection">
    `accountCollection()` takes a normal collection config and adds the auth settings, access, rate limit, and emails for site visitors:

    ```ts src/collections/Customers.ts
    import { accountCollection } from "@adirishi/offload-accounts/config";
    import { getBindings } from "@adirishi/offload-cloudflare";

    const env = await getBindings();

    export const Customers = accountCollection(
      {
        slug: "customers",
        fields: [{ name: "name", type: "text" }],
      },
      { siteURL: env.SITE_URL, rateLimit: () => env.ACCOUNTS },
    );
    ```

    Pass `rateLimit` as a function. Cloudflare's upload validation loads the config without bindings, and the function reads the binding only when a login runs.

    Add the collection to the config, and name the admin's collection in `admin.user`. Without `admin.user`, Payload makes the first auth collection in `collections` the admin's:

    ```ts src/payload.config.ts
    export default buildConfig({
      admin: { user: Users.slug },
      collections: [Users, Customers, Pages, Posts, Media],
      // db, editor, email, plugins
    });
    ```

    Run `pnpm payload migrate:create`, then `pnpm payload generate:types`.

    [The package reference](/accounts#accountcollection) lists what `accountCollection()` sets and how to change it.

  </Step>
  <Step title="Check the collection in every access rule">
    Once a second auth collection exists, `req.user` can be a customer. An access rule such as `({ req }) => Boolean(req.user)` then lets every customer in. Replace each rule that means "an editor" with `isAdminUser`, which is `true` only for a user of the collection that `admin.user` names:

    ```ts src/collections/Pages.ts
    import { isAdminUser } from "@adirishi/offload-accounts/config";

    access: {
      create: isAdminUser,
      read: ({ req }) => req.user?.collection === "users" || { _status: { equals: "published" } },
      update: isAdminUser,
      delete: isAdminUser,
    },
    ```

    `isAdminUser` checks only the collection. If `users` also holds people whom `access.admin` turns away, check their role too.

    `getPayloadForRequest()` from `@adirishi/offload-tanstack` already gives drafts only to users who can open the admin, so a logged-in customer sees published pages.

    For documents that belong to one customer, such as bookings or orders, use `adminOrOwner()`. It gives admin users every document, and a customer the documents whose relationship field points at them:

    ```ts src/collections/Bookings.ts
    import type { CollectionConfig } from "payload";

    import { adminOrOwner, isAdminUser } from "@adirishi/offload-accounts/config";

    export const Bookings: CollectionConfig = {
      slug: "bookings",
      access: {
        create: isAdminUser,
        read: adminOrOwner("customers", "customer"),
        update: isAdminUser,
        delete: isAdminUser,
      },
      fields: [
        { name: "title", type: "text", required: true },
        { name: "customer", type: "relationship", relationTo: "customers", required: true },
      ],
    };
    ```

  <Step title="Write the server functions">
    The registry components import their server functions from `@/server/account.functions`. Create that file:

    ```ts src/server/account.functions.ts
    import {
      changePasswordInput,
      forgotPasswordInput,
      logInInput,
      resetPasswordInput,
      signUpInput,
      verifyEmailInput,
    } from "@adirishi/offload-accounts";
    import { getBindings } from "@adirishi/offload-cloudflare";
    import { hideServerErrors } from "@adirishi/offload-tanstack";
    import { createServerFn } from "@tanstack/react-start";
    import { z } from "zod";

    import { accounts } from "@/lib/accounts.server";

    export const getAccount = createServerFn({ method: "GET" })
      .middleware([hideServerErrors])
      .handler(async () => {
        const account = await accounts.getAccount();
        return account && { id: account.id, email: account.email, name: account.name };
      });

    export const logIn = createServerFn({ method: "POST" })
      .middleware([hideServerErrors])
      .validator(logInInput)
      .handler(({ data }) => accounts.logIn(data));

    export const logOut = createServerFn({ method: "POST" })
      .middleware([hideServerErrors])
      .validator(z.object({ everywhere: z.boolean().optional() }))
      .handler(({ data }) => accounts.logOut(data));

    export const signUp = createServerFn({ method: "POST" })
      .middleware([hideServerErrors])
      .validator(signUpInput)
      .handler(async ({ data }) => {
        const env = await getBindings();
        return accounts.signUp(data, { turnstileSecret: env.TURNSTILE_SECRET_KEY });
      });

    export const requestPasswordReset = createServerFn({ method: "POST" })
      .middleware([hideServerErrors])
      .validator(forgotPasswordInput)
      .handler(async ({ data }) => {
        const env = await getBindings();
        return accounts.requestPasswordReset(data, { turnstileSecret: env.TURNSTILE_SECRET_KEY });
      });

    export const resetPassword = createServerFn({ method: "POST" })
      .middleware([hideServerErrors])
      .validator(resetPasswordInput)
      .handler(({ data }) => accounts.resetPassword(data));

    export const verifyEmail = createServerFn({ method: "POST" })
      .middleware([hideServerErrors])
      .validator(verifyEmailInput)
      .handler(({ data }) => accounts.verifyEmail(data));

    export const changePassword = createServerFn({ method: "POST" })
      .middleware([hideServerErrors])
      .validator(changePasswordInput)
      .handler(({ data }) => accounts.changePassword(data));
    ```

    `getAccount` returns only the fields that the pages show. The account document also holds its `sessions`, so never return the whole document to the browser.

    To collect more fields at sign-up, such as a name, extend the input with `signUpInput.extend({ name: z.string().max(100) })`, and pass the validated fields as `data`: `accounts.signUp(data, { turnstileSecret, data: { name: data.name } })`. Add the field to the sign-up form too.

  <Step title="Load the account in the layout">
    Read the account once per navigation in the `_frontend` layout route, and put it in the route context. The pages below it read it from there:

    ```tsx src/app/_frontend.tsx
    import { createFileRoute, Outlet } from "@tanstack/react-router";

    import { AccountMenu } from "@/components/accounts/account-menu";
    import { getAccount } from "@/server/account.functions";

    export const Route = createFileRoute("/_frontend")({
      beforeLoad: async () => ({ account: await getAccount() }),
      component: FrontendLayout,
    });

    function FrontendLayout() {
      const { account } = Route.useRouteContext();
      return (
        <>
          <header className="flex justify-end p-4">
            <AccountMenu account={account} />
          </header>
          <Outlet />
        </>
      );
    }
    ```

    `getAccount()` returns `null` for a visitor and for a logged-in editor. When it finds an account, it marks the response `Cache-Control: private, no-store`, so a shared cache never stores a page that shows the account, and it extends the session.

  <Step title="Guard the account pages">
    Put the pages that need an account under a pathless `_account` route. Its `beforeLoad` sends a visitor who isn't logged in to `/login`, with the page they asked for in `returnTo`:

    ```tsx src/app/_frontend/_account.tsx
    import { createFileRoute, Outlet, redirect } from "@tanstack/react-router";

    export const Route = createFileRoute("/_frontend/_account")({
      beforeLoad: ({ context, location }) => {
        if (!context.account) {
          throw redirect({ to: "/login", search: { returnTo: location.href } });
        }
        return { account: context.account };
      },
      component: Outlet,
    });
    ```

    ```tsx src/app/_frontend/_account/account.index.tsx
    import { createFileRoute } from "@tanstack/react-router";

    export const Route = createFileRoute("/_frontend/_account/account/")({
      component: AccountPage,
    });

    function AccountPage() {
      const { account } = Route.useRouteContext();
      return (
        <main>
          <h1>Your account</h1>
          <p>Logged in as {account.name || account.email}.</p>
        </main>
      );
    }
    ```

    The guard only decides where the browser goes. A server function that reads private data checks the account again with `requireAccount()`, and passes it as `user` with `overrideAccess: false`, so the collection's access decides what it returns:

    ```tsx src/app/_frontend/_account/account.bookings.tsx
    import { hideServerErrors } from "@adirishi/offload-tanstack";
    import { createFileRoute } from "@tanstack/react-router";
    import { createServerFn } from "@tanstack/react-start";

    import { accounts } from "@/lib/accounts.server";
    import { getVisitorPayload } from "@/lib/payload.server";

    const getBookings = createServerFn({ method: "GET" })
      .middleware([hideServerErrors])
      .handler(async () => {
        const [account, payload] = await Promise.all([accounts.requireAccount(), getVisitorPayload()]);
        const { docs } = await payload.find({
          collection: "bookings",
          depth: 0,
          overrideAccess: false,
          user: account,
        });
        return docs.map(({ id, title }) => ({ id, title }));
      });

    export const Route = createFileRoute("/_frontend/_account/account/bookings")({
      loader: () => getBookings(),
      component: BookingsPage,
    });

    function BookingsPage() {
      const bookings = Route.useLoaderData();
      return (
        <ul>
          {bookings.map((booking) => (
            <li key={booking.id}>{booking.title}</li>
          ))}
        </ul>
      );
    }
    ```

## Check the result

1. Run `pnpm vite build` and `pnpm vite preview`, and open `/sign-up` in a private window.
2. Sign up. The form asks you to check your email.
3. Open the local email explorer at `/cdn-cgi/local/explorer`, and follow the link in "Confirm your email address", and press **Confirm email address**. The page says the email is verified.
4. Log in. The header shows the account menu.
5. Choose **Log out** in the account menu, then open `/account`. The site sends you to the login page, and after you log in, back to `/account`.

Run the checks on a production build. `vite dev` runs in Node, where some Workers behaviour doesn't show.

Before you deploy, set `SITE_URL` for the deployed environment, and [use real Turnstile keys](/forms#use-real-turnstile-keys). One widget serves the sign-up form, the forgot-password form, and the site's other forms. Each form sends its own action, `sign-up` or `forgot-password`, and the server rejects a token for another action.

## One login per browser

Payload names its auth cookie `<cookiePrefix>-token`, `payload-token` by default, for every auth collection. The site and `/admin` share one origin, so a browser holds one Payload session at a time. A customer who logs in on the site replaces an editor's admin session in that browser, and an editor who logs in to the admin replaces a customer's session. The token's collection decides who the user is, so neither user gets the other's access.

To test the site as a customer while you edit content, use a second browser or a private window.

## Rate limits replace lockout

Payload locks an account after five failed logins by default. Anyone who knows a customer's email could then keep that customer locked out, so `accountCollection()` turns lockout off with `maxLoginAttempts: 0`.

The `ACCOUNTS` binding limits these instead:

- Logins, per visitor IP. A limit per email would lock a customer out the same way lockout does, because anyone can spend an email's allowance with a few wrong guesses a minute. Wrong passwords use up only the allowance of the IP that sends them.
- Password reset requests, per visitor IP and per email. The email limit stops anyone from flooding one inbox with reset emails. Payload also sends one account at most one reset email every 15 seconds.

The limit runs as a `beforeOperation` hook, so it also covers Payload's REST endpoints, `POST /api/customers/login` and `POST /api/customers/forgot-password`, which answer 429 over the limit. The server functions return `limited`. `changePassword()` checks the current password with a login, so it shares the login limit.

The binding counts per Cloudflare location, and its counts are eventually consistent. It slows down password guessing from one IP, but it isn't an exact limit, and it doesn't stop guessing spread over many IPs. Sign-up has no rate limit. Turnstile protects it.

## Sign-up doesn't reveal which emails have accounts

Sign-up answers `check-email` both for a new email and for an email that already has an account. The existing account gets a password reset email that says someone tried to sign up with the address. The forgot-password form answers `sent` whether or not the email has an account.

With email verification on, which is the default, nothing that the site shows tells a visitor which emails are registered. To turn verification off, pass `verify: false` to `accountCollection()`. A new account then logs in at once, while an existing email still gets `check-email`, so sign-up shows which emails are new.

Response times can still show which emails are registered. Payload's login hashes the password only for an email that has an account, and answers at once for an unknown email, so a failed login for a registered email takes about 10 ms longer. Sign-up and password reset requests also do different work for the two cases. The login rate limit per IP slows down anyone who probes many emails this way, but hiding the difference needs a change in Payload's login.

## Sessions last 14 days and slide

A login lasts 14 days. When the session has used half of that, `getAccount()` replaces the cookie with a new 14-day one, so an active customer stays logged in, and a customer who stays away for 14 days logs in again. To change the lifetime, set `auth.tokenExpiration` in seconds on the collection.

The refresh relies on an [Offload patch](/patches/concurrent-session-refresh) that makes Payload's refresh update the one session it extends. Without it, a refresh on D1 rewrites every session of the account and can fail during a login on another device.

**Log out everywhere** in the account menu ends every session of the account. A password reset ends every session except the one that it starts.

## Accounts need the Workers Paid plan

The [PBKDF2 patch](/patches/workers-pbkdf2-cap) hashes passwords with 100,000 iterations, which costs about 10 ms of CPU per hash. A login, a sign-up, and a password reset each hash a password. The Workers Free plan allows 10 ms of CPU per request in total, so on Free those requests fail when the hash and Payload's own work pass the limit. The Paid plan allows 30 seconds by default.

## Create customers through the Worker

A password hash made in Node, through `vite dev`, the Payload CLI, or a seed script, uses 600,000 iterations, and a deployed Worker can't verify it. Create customers through sign-up, the deployed admin, or the deployed REST API, and never from a seed script. [Known limits](/limits#passwords) has the details.

Payload gives every auth collection `POST /api/<slug>/first-register`, which creates the first account of an empty collection past access control. `accountCollection()` answers it with 403, so the first customer signs up like the rest.

## Email and password changes

Payload lets a user change their own email and password through REST, with no current password and without verifying the new email. A stolen session could then lock the real customer out for good. `accountCollection()` refuses an update that changes `email` or sets `password`, with a 403, unless the user is one of the admin's users or the server code passes `overrideAccess: true`. A customer can still update other fields of their own account, such as a name.

A customer changes their password on the page above, through `changePassword()`. It checks the current password first, keeps the customer logged in, and ends their other sessions. Changing an account's email is for the admin's users only in this version, through the admin.

## Change the emails

The verification and reset emails link to the site's own pages, `/verify-email` and `/reset-password` under `siteURL`, and never to `/admin`. If the site's pages have other paths, set `paths`. To write the emails yourself, set `emails`. Each function receives the link to put in the email:

```ts src/collections/Customers.ts
export const Customers = accountCollection(
  { slug: "customers", fields: [{ name: "name", type: "text" }] },
  {
    siteURL: env.SITE_URL,
    rateLimit: () => env.ACCOUNTS,
    paths: { resetPassword: "/auth/reset-password", verifyEmail: "/auth/verify-email" },
    emails: {
      verifyEmail: ({ url }) => ({
        subject: "Confirm your email address",
        html: `<p><a href="${url}">Confirm your email address</a></p>`,
      }),
    },
  },
);
```

`siteURL` is required, so a request's `Host` header never decides where the links point.

## Keep CSRF protection

Payload checks the `Origin` of each request that authenticates with the cookie. Setting `serverURL` adds it to `csrf`, and once `csrf` lists an origin, Payload accepts the cookie only from the origins in the list. If the config sets `serverURL`, list every origin that serves the site in `csrf`, such as a `workers.dev` preview host. Otherwise a customer on an unlisted host looks logged out.

TanStack Start protects server functions with its CSRF middleware when the site has no `src/start.ts`. If the site adds `src/start.ts` with its own `requestMiddleware`, add `createCsrfMiddleware({ filter: (ctx) => ctx.handlerType === "serverFn" })` from `@tanstack/react-start` to it.

## Social login and magic links

Payload v4 has no OAuth, social login, magic link, or two-factor login, and this version of `@adirishi/offload-accounts` doesn't add them. Customers log in with an email and a password.

## Use the customers with the e-commerce plugin

Payload's e-commerce plugin, `@payloadcms/plugin-ecommerce`, links carts, orders, addresses, and transactions to a customers collection. [Known limits](/limits#not-tested) lists it as untested on Workers.

Point the plugin at the account collection with `customers: { slug: "customers" }`. The plugin's carts, orders, addresses, and transactions each get a `customer` relationship to that collection. The plugin doesn't change the customers collection itself.

The plugin's access rules come from the site, and its examples check a `roles` field on one `users` collection. With a separate customers collection, check the collection instead. User IDs of `users` and `customers` can be equal, so an ownership rule must check the collection as well as the ID:

```ts src/payload.config.ts
import { adminOrOwner, isAdminUser } from "@adirishi/offload-accounts/config";
import { ecommercePlugin } from "@payloadcms/plugin-ecommerce";

ecommercePlugin({
  customers: { slug: "customers" },
  access: {
    isAdmin: isAdminUser,
    adminOnlyFieldAccess: ({ req }) => req.user?.collection === "users",
    adminOrPublishedStatus: ({ req }) =>
      req.user?.collection === "users" || { _status: { equals: "published" } },
    isCustomer: ({ req }) => req.user?.collection === "customers",
    isDocumentOwner: adminOrOwner("customers", "customer"),
  },
});
```

`isCustomer` decides whose new addresses the plugin assigns to the user who creates them. An editor who creates an address in the admin chooses its customer.

Add a `cart` join field to the customers collection: `{ name: "cart", type: "join", collection: "carts", on: "customer" }`. The plugin's React provider and its payment endpoint read the customer's cart from it.

The plugin keeps a guest's cart in `localStorage`. When the guest logs in, `onLogin()` from `useEcommerce()` merges the guest cart into the customer's cart, or gives the guest cart to the customer. The plugin's examples call it after a REST login. With this guide's login form, call it in the form when `logIn` returns `signed-in`, before the form navigates, and call `onLogout()` after `logOut`. Render `EcommerceProvider` with `customersSlug="customers"`, because it reads the customer from `/api/<customersSlug>/me`.
