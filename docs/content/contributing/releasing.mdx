title: Releasing
description: How every change that passes CI on main becomes a release on GitHub Packages, and how releases are versioned, tagged, and attested.
---

Releases are automatic. Push to `main`, and once its checks pass, the CI run publishes the change to [GitHub Packages](https://github.com/AdiRishi?tab=packages&repo_name=offload-cms) if it changes what the packages ship. Nobody edits a version.

## Versions

Every package in a release has the same version, `<Payload version>-offload.<n>`, such as `4.0.0-beta.2-offload.4`. `<n>` counts Offload's releases on that Payload tag. The first release after an upgrade to a new Payload tag is `-offload.0`.

Each release has a git tag, `v<version>`, on the commit it was published from. The newest tag for the pinned Payload tag is the latest release.

## What the Publish job does

The Publish job runs `pnpm release publish` on the commit that passed the checks:

1. Find the latest release tag for the pinned Payload tag.
2. Stop if the commit is already part of that release, or if nothing the packages ship changed since it. Shipped files are `packages/`, `release/src/`, `release/package.json`, `upstream/patches/`, and `upstream/payload.json`. `AGENTS.md` files and tests don't count.
3. Build `upstream/payload` and `packages/` through Turborepo. The Payload build stops if `upstream/payload` doesn't match the pin and the patches.
4. Pack every package with pnpm. Each Payload package becomes `@adirishi/offload-<name>` at the new version, with internal dependencies rewritten to npm aliases and a README that points back to Offload.
5. Publish the tarballs to `OFFLOAD_REGISTRY`, with `OFFLOAD_REGISTRY_TOKEN` when the registry needs one.
6. Tag the commit `v<version>` and push the tag.

Offload's own packages are the public workspace packages that `release/package.json` depends on.

To try a change without releasing it, run `pnpm release e2e`. It publishes the working tree as `<Payload version>-offload.dev` to a registry that exists only for that run.

## Provenance

npm's `--provenance` works only on the public npm registry. Instead, the Publish job signs each published tarball with [`actions/attest`](https://github.com/actions/attest). The attestation is SLSA build provenance, recorded through Sigstore, and names the commit, workflow, and run that produced the file. `publish` uploads the exact tarballs that the job attests. [Update Offload](/update#verify-a-package) shows how a site checks a package.

## Continuous integration

Every pull request and every push to `main` runs the CI workflow. These jobs run in parallel:

- `pnpm check`
- the e2e suite on D1 and on Postgres, against the working tree published to a registry inside the runner

On `main`, the same run continues once both pass. The Publish job releases the commit, then the docs jobs build and deploy this site, so the docs show the latest release. A run on `main` waits for the previous one to finish instead of cancelling it. To retry a failed publish or deploy, re-run the failed jobs in the run.
