`e2e` is a Payload site on Cloudflare Workers that exists to be tested. It installs Offload from a registry the way a real site does, and Playwright drives its Worker build in local workerd. The suite tests what Offload changes or depends on, plus the main editor flows. Payload's own test suite covers Payload's features.

## Run the suite

```bash
pnpm release e2e
pnpm release e2e --postgres
```

The Postgres run needs Docker. CI runs both on every pull request and every push to `main`. Each run does these steps:

1. Start a registry that exists only for the run, and publish the working tree to it.
2. Install `e2e` from that registry. Every run publishes the same version, so the install starts from an empty `node_modules`.
3. Type-check and lint `e2e`. The type-aware lint rules need `e2e`'s dependencies, so `pnpm check` skips `e2e`. `e2e/.oxlintrc.json` extends the root config, and the root `pnpm lint` passes `--disable-nested-config` so that it doesn't read it. Then check that each migration matches the schema. See [Change the schema](#change-the-schema).
4. Reset the local D1 and R2 state, or the Postgres schema. Apply the migrations, create a page, drop the database with `migrate:fresh`, roll back every migration with `migrate:down`, and apply them again. Then build the Worker.
5. Serve the build with `vite preview`, create the first admin user through the admin panel, and run the suite.
6. Start `vite dev`, edit the Payload config and a collection, and check that Payload keeps working after each reload. The check restores the files it edits. `playwright.dev.config.ts` runs this check after the main suite, because two local processes on one D1 database fail.
7. On D1, check the Worker's compressed size against its budget.

## Worker size budget

The D1 run ends with `pnpm size` in `e2e`. It builds the Worker and reads its compressed size from `wrangler deploy --dry-run`, which needs no Cloudflare account and contacts no Cloudflare API. The check fails when the size passes the budget in `e2e/scripts/worker-size.ts`, so a change that bundles a large dependency or a second copy of Payload fails CI. To check the size after a change, run:

```bash
pnpm e2e:size
```

If the growth is intended, raise the budget in the same commit and keep about 5% of headroom.

## Rerun the suite without publishing

After one `pnpm release e2e`, `e2e` has the release installed. Run `pnpm e2e:test`, or `pnpm e2e:test:postgres` for Postgres. `pnpm e2e:test:dev` reruns only the `vite dev` check. It signs in with the admin that the main suite created.

To read the Worker's logs, start the server yourself:

```bash
pnpm e2e:serve
```

Then run the suite from another terminal. It uses the running server:

```bash
pnpm e2e:test:reuse
```

## What the suite covers

Each file in `e2e/tests/` is named for the area it covers, and each test's title says what it checks.

The suite runs with Cloudflare's Turnstile testing secret, which passes every token, so no end-to-end test sees Turnstile reject a token. The tests of `verifyTurnstile()` in `packages/cloudflare` cover a rejected token, a token from another host or action, and a Siteverify outage.

## How the site is set up

`src/payload.config.ts` picks the database adapter from the binding that exists: `wrangler.jsonc` binds D1 by default, and its `postgres` environment binds Hyperdrive to the Docker Postgres in `docker-compose.yml`. The customers collection has 90-second sessions, so a test sees one slide. `stubs/razorpay.ts` and `stubs/mips.ts` stand in for the gateways on ports 4890 and 4891, with real signing, and test-only `/__stub/` routes pay an order and return each webhook or IMN as sent.

The `/api/e2e/*` endpoints exist only for the suite. Payload closes its jobs collection to REST, and a real site should keep it closed.

## Change the schema

Each local run of the suite starts from an empty database, so `e2e` keeps exactly one migration per database: `src/migrations/d1/*_initial` and `src/migrations/postgres/*_initial`. A schema change rewrites that migration in place. It never adds a migration file, so a pull request's diff shows only the schema change. Payload skips a migration whose name a database has already recorded, so [`pnpm e2e:deploy:staging`](#test-on-cloudflare) resets the staging database instead of migrating it.

After you change a collection, a global, or a plugin's options, run this. It needs the release that `pnpm release e2e` installs:

```bash
pnpm e2e:migrations:regenerate
```

For each database, `scripts/migrations.ts` runs Payload's `createMigration` in an empty temporary directory, as `payload migrate:create initial` does in an empty migrations directory. drizzle-kit generates the whole schema, which keeps the SQL, indexes, foreign keys, and the order of D1's `DROP TABLE` statements correct. The script writes the result over the committed `_initial.ts` and keeps its name. `migrate:create` doesn't connect to the database, so the Postgres run doesn't need Docker.

`pnpm release e2e` runs `pnpm migrations:check` after it lints `e2e`. The check generates the same migrations and fails with a diff when a committed migration differs, so a schema change without a regenerated migration fails CI. It also fails when a migrations directory holds a second migration.

The repository keeps no drizzle-kit `.json` snapshots, because nothing reads them: every regeneration starts from an empty directory, and `payload migrate` runs only the `.ts` files. Don't run `pnpm payload migrate:create` in `e2e`. Without a snapshot to diff against, it writes a second migration with the whole schema. `.gitignore` excludes the snapshot that it writes.

## Test on Cloudflare

Some behaviour shows up only on a deployed Worker, such as the Workers limit on PBKDF2 iterations, which local workerd doesn't enforce and the [PBKDF2 patch](/patches/workers-pbkdf2-cap) works around. The `staging` environment in `wrangler.jsonc` deploys `e2e` as `offload-e2e-staging`, with its own D1 database and R2 bucket. Run:

```bash
pnpm e2e:deploy:staging
```

The command runs `payload migrate:fresh --force-accept-warning` on the remote D1 database, which drops every table and applies the migrations to the empty database. Then it builds for staging and deploys. Staging holds only test data, and the reset is what applies a rewritten `initial` migration. The reset also deletes the staging admin, so create it again on the admin's first-user screen with the credentials in `e2e/.staging-admin.json`, which git ignores. `PAYLOAD_SECRET` is a Wrangler secret on the Worker.
