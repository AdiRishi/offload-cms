`e2e` is a Payload site on Cloudflare Workers that exists to be tested. It installs Offload from a registry the way a real site does, and Playwright drives its Worker build in local workerd. The suite tests what Offload changes or depends on, plus the main editor flows. Payload's own test suite covers Payload's features.

## Run the suite

```bash
pnpm release e2e
pnpm release e2e --postgres
```

The Postgres run needs Docker. CI runs both on every pull request and every push to `main`. Each run does these steps:

1. Start a registry that exists only for the run, and publish the working tree to it.
2. Install `e2e` from that registry. Every run publishes the same version, so the install starts from an empty `node_modules`.
3. Type-check and lint `e2e`. The type-aware lint rules need `e2e`'s dependencies, so `pnpm check` skips `e2e`. `e2e/.oxlintrc.json` extends the root config, and the root `pnpm lint` passes `--disable-nested-config` so that it doesn't read it.
4. Reset the local D1 and R2 state, or the Postgres schema. Apply the migrations, create a page, drop the database with `migrate:fresh`, roll back every migration with `migrate:down`, and apply them again. Then build the Worker.
5. Serve the build with `vite preview`, create the first admin user through the admin panel, and run the suite.
6. Start `vite dev`, edit the Payload config and a collection, and check that Payload keeps working after each reload. The check restores the files it edits. `playwright.dev.config.ts` runs this check after the main suite, because two local processes on one D1 database fail.
7. On D1, check the Worker's compressed size against its budget.

## Worker size budget

The D1 run ends with `pnpm size` in `e2e`. It builds the Worker and reads its compressed size from `wrangler deploy --dry-run`, which needs no Cloudflare account and contacts no Cloudflare API. The check fails when the size passes the budget in `e2e/scripts/worker-size.ts`, so a change that bundles a large dependency or a second copy of Payload fails CI. To check the size after a change, run this from `e2e`:

```bash
pnpm size
```

If the growth is intended, raise the budget in the same commit and keep about 5% of headroom.

## Rerun the suite without publishing

After one `pnpm release e2e`, `e2e` has the release installed. From `e2e`, run `pnpm test`, or `CLOUDFLARE_ENV=postgres pnpm test` for Postgres. `pnpm test:dev` reruns only the `vite dev` check. It signs in with the admin that the main suite created.

To read the Worker's logs, start the server yourself:

```bash
node scripts/prepare.ts && pnpm preview
```

Then run the suite from another terminal. It uses the running server:

```bash
E2E_REUSE_SERVER=1 pnpm exec playwright test
```

## How the site is set up

| File                                           | Purpose                                                                                                                                   |
| ---------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `wrangler.jsonc`                               | D1, R2, Images, and Email Service by default. The `postgres` environment binds Hyperdrive to the Docker Postgres in `docker-compose.yml`. |
| `src/payload.config.ts`                        | Picks the database adapter from the binding that exists                                                                                   |
| `src/migrations/d1`, `src/migrations/postgres` | One `initial` migration per database. See [Change the schema](#change-the-schema).                                                        |
| `src/jobs.ts`                                  | A job task, a workflow, and two endpoints that queue work for the Cron Trigger                                                            |
| `src/collections/FieldTypes.ts`                | Every field type that works on both SQLite and Postgres                                                                                   |
| `src/blocks.ts`                                | A block defined in the config's `blocks`, which pages and the posts editor reference by slug                                              |

The `/api/e2e/*` endpoints exist only for the suite. Payload closes its jobs collection to REST, and a real site should keep it closed.

## Change the schema

Each local run of the suite starts from an empty database, so `e2e` keeps exactly one migration per database: `src/migrations/d1/*_initial` and `src/migrations/postgres/*_initial`. A schema change rewrites that migration in place. It never adds a migration file, so a pull request's diff shows only the schema change. Payload skips a migration whose name a database has already recorded, so [`pnpm deploy:staging`](#test-on-cloudflare) resets the staging database instead of migrating it.

drizzle-kit writes the new migration, which keeps the SQL, indexes, foreign keys, and the order of D1's `DROP TABLE` statements correct. For each database, run these steps from `e2e`:

1. Move every file in `src/migrations/d1` to a temporary directory.
2. Generate the whole schema. With no earlier snapshot in the directory, drizzle-kit compares the schema with an empty database:

   ```bash
   pnpm payload migrate:create initial
   ```

3. Copy the generated `.ts` and `.json` files over the `_initial` files in the temporary directory, and keep the old file names.
4. Delete the generated files, including the new `index.ts`, and move the files from the temporary directory back.
5. Check that the migration matches the schema. This command prints `Cancelled.` and creates no file:

   ```bash
   pnpm payload migrate:create --skip-empty
   ```

For Postgres, use `src/migrations/postgres` and prefix each command with `CLOUDFLARE_ENV=postgres`. `migrate:create` doesn't connect to the database, so these steps don't need Docker. `.gitattributes` marks the `.json` snapshots as generated, so GitHub collapses them in diffs.

## Test on Cloudflare

Some behaviour shows up only on a deployed Worker, such as the Workers limit on password hashing that the [PBKDF2 patch](/patches/workers-pbkdf2-cap) works around. The `staging` environment in `wrangler.jsonc` deploys `e2e` as `offload-e2e-staging`, with its own D1 database and R2 bucket. From `e2e`, run:

```bash
pnpm deploy:staging
```

The command runs `payload migrate:fresh --force-accept-warning` on the remote D1 database, which drops every table and applies the migrations to the empty database. Then it builds for staging and deploys. Staging holds only test data, and the reset is what applies a rewritten `initial` migration. The reset also deletes the staging admin, so create it again on the admin's first-user screen with the credentials in `e2e/.staging-admin.json`, which git ignores. `PAYLOAD_SECRET` is a Wrangler secret on the Worker.
