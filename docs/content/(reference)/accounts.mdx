The main entry point holds the input schemas and result types, and runs in the browser and on the server. `/config` belongs in the Payload config and doesn't import TanStack Start. `/server` reads the request through TanStack Start, so it runs only in server functions and server components. The forms come from the [registry](#registry). [Add customer accounts](/customer-accounts) installs the package and sets up a site.

## accountCollection()

`accountCollection(collection, options)` returns an auth collection for the site's visitors, such as customers or members. Its TSDoc lists what it sets.

The keys of the collection's own `auth`, `access`, and `admin` replace the preset's one key at a time. `auth.cookies` merges over the preset's cookie, so `auth: { cookies: { domain: "example.com" } }` keeps `secure` and `sameSite`. `auth.forgotPassword` merges too, but the email functions always come from `options`.

`rateLimit` returns the binding instead of taking it, because Cloudflare's upload validation loads the config without bindings. The hooks call it only when a login or a reset request runs.

### Rate limit

The hook runs for the collection's `login` and `forgotPassword` operations, whether they come from the server helpers, the Local API, or `POST /api/<slug>/login` and `POST /api/<slug>/forgot-password`. It counts every attempt before Payload checks the password.

A login counts once against the key `<slug>:login:ip:<ip>`. A reset request counts against `<slug>:forgot-password:ip:<ip>` and `<slug>:forgot-password:email:<email>`. `<ip>` is the `cf-connecting-ip` header, and `<email>` is the address trimmed and in lowercase. `vite dev` doesn't set the header, so it doesn't limit logins at all.

Logins have no key per email. Anyone could spend an email's allowance with a few wrong guesses a minute and keep the customer out, which is the lockout that `maxLoginAttempts: 0` turns off. Reset requests have one, so nobody floods an inbox.

Over the limit, the hook throws a public `APIError` with status 429. REST answers 429, and the server helpers return `limited`. The binding counts per Cloudflare location and is eventually consistent, so it slows guessing from one IP but doesn't stop guessing spread over many IPs. Sign-up has no rate limit. Turnstile protects it.

### Email and password changes

Payload lets a user who may update their own document change its `email` and `password` through REST, with no current password and without verifying the new email. A stolen session could then keep the account. So an `update` that changes `email` or sets `password` fails with a public `APIError` with status 403, unless the user is a user of `admin.user` or the call passes `overrideAccess: true`. Other fields, such as a `name`, stay open to the account.

An account changes its password with [`changePassword()`](#changepassword), which checks the current password first. Only the admin's users change an account's email.

### First register

Payload gives every auth collection `POST /api/<slug>/first-register`, which creates the first document of an empty collection past access control and marks it verified. The preset answers it with 403, so the first customer signs up like the rest.

### Emails

Each email links to a page under `siteURL`, with the token in a `token` search parameter, such as `https://example.com/reset-password?token=<token>`. The default pages are `/login`, `/reset-password`, and `/verify-email`, which the [registry](#registry) forms link to. `paths` changes them.

| Email            | Sent when                                                  |
| ---------------- | ---------------------------------------------------------- |
| Verification     | An account is created, while `verify` is on                |
| Password reset   | A visitor asks to reset their password                     |
| Existing account | Someone signs up with an email that already has an account |

The existing-account email goes through `emails.resetPassword` with `logInURL` set, so one template writes both. A reset link works once, for `auth.forgotPassword.expiration`, which defaults to one hour. Payload sends at most one reset email per account every 15 seconds, through `auth.forgotPassword.minRequestInterval`, and skips the others without an error.

## isAdminUser

Use it in place of rules such as `({ req }) => Boolean(req.user)`, which let in a user of any auth collection. It checks only the collection and doesn't run the collection's `access.admin`, so it also returns `true` for a user of that collection whom `access.admin` turns away.

## adminOrOwner()

`adminOrOwner("customers", "customer")` gives the admin's users every document, and a customer the documents whose `customer` relationship points at them. It checks the user's collection as well as the ID, because a user of `admin.user` and an account can have the same ID.

## createAccountHelpers()

Returns the server helpers for one account collection. A site calls it once, in a server-only module, and calls the helpers from its own `createServerFn()` handlers.

The helpers pass the request's headers to Payload, so hooks see the visitor's IP and cookies. A helper that takes visitor input returns a result with a `status`, and doesn't throw. It logs an unexpected error and returns `error`.

### getAccount()

Returns `null` for a visitor who isn't logged in and for a user of another collection, such as an editor. It runs Payload's auth strategies on the request's headers, without computing permissions. It is wrapped in React's `cache()`, so the server components of one render share one lookup.

When it finds an account, it:

- Sets `Cache-Control: private, no-store` on the response, so a shared cache never stores a page that shows the account.
- Extends the session when the cookie's token has half of `tokenExpiration` or less left. It runs Payload's refresh, and sets a cookie with a new token for the full `tokenExpiration`, 14 days by default. An active customer stays logged in, and one who stays away for 14 days logs in again. A token from an `Authorization` header doesn't slide.

The refresh relies on an [Offload patch](/patches/concurrent-session-refresh) that updates the one session it extends. Without it, a refresh on D1 rewrites every session of the account and can fail during a login on another device.

The account is the whole document, including `sessions`. Return only the fields a page needs from a server function.

### requireAccount()

Throws TanStack Router's `redirect()` to `loginPath` when `getAccount()` returns `null`. The redirect carries no `returnTo`. Call it in each server function that reads private data, and pass the account as `user` with `overrideAccess: false`.

### logIn()

`signed-in` carries `returnTo` when Payload's `getSafeRedirect()` accepts it as a path on the site, and `accountPath` otherwise.

### logOut()

Ends the session of the request's user, or every session of that user with `{ everywhere: true }`, and expires the cookie. It ends the session of a user from any collection, an editor included.

### signUp()

1. Checks `turnstileToken` with [`verifyTurnstile()`](/cloudflare#verifyturnstile), for the request's hostname and the action `sign-up`. A token that fails returns `unverified`.
2. If an account has the email, sends it the existing-account email and returns `check-email`. The email goes through the `forgotPassword` operation and its rate limit. Over the limit, it sends nothing and still returns `check-email`.
3. Creates the account with `email`, `password`, and `data`, with access control bypassed. A field that fails the collection's validation returns `invalid`, with each message in `errors` by field path. A duplicate email from a sign-up that finished first is handled as in step 2.
4. With verification on, Payload sends the verification email, and the result is `check-email`. With `verify: false`, it logs the visitor in and returns `signed-in`.

`data` bypasses access control, so validate the site's own fields in the server function before you pass them.

### requestPasswordReset()

Checks `turnstileToken` for the action `forgot-password`, then runs Payload's `forgotPassword` operation. It returns `sent` whether or not the email has an account.

### resetPassword()

Payload ends every session of the account and starts a new one, and the helper sets its cookie. With verification on, it also marks the account as verified, because the email proves the visitor owns the address.

### verifyEmail()

It doesn't log the visitor in. Call it from a POST server function when the visitor presses a button, never from a page's loader, because mail scanners open the links in emails.

### changePassword()

It checks `currentPassword` with a login, which shares the login [rate limit](#rate-limit). Then Payload keeps the visitor's session and ends the account's other sessions.

## Input schemas

Pass each schema to the server function's `.validator()`. The registry forms validate with the same schemas in the browser. The `email` schema trims and lowercases the address, so the rate limit and the existing-account check see one form of it. To collect more fields at sign-up, extend the schema: `signUpInput.extend({ name: z.string().max(100) })`.

## Results

These statuses mean more than their names say:

- `check-email` from `signUp` answers a new account and an existing email alike, and `sent` from `requestPasswordReset` answers whether or not the email has an account. Neither shows which emails are registered.
- `invalid` from `logIn` covers an unknown email and a wrong password, without saying which. `email-unverified` comes only after a correct password.
- `unverified` means the Turnstile check failed, not the email.
- `locked` comes only from a collection that sets `auth.maxLoginAttempts`.
- `limited` from `changePassword` comes from the login rate limit.

## Registry

Offload's shadcn registry installs the account forms as source files that the site owns and edits. The docs build publishes each item at `https://adirishi.github.io/offload-cms/r/<item>.json`, from [`packages/accounts/registry.json`](https://github.com/AdiRishi/offload-cms/blob/main/packages/accounts/registry.json). `form-fields` and `turnstile` come from the [form-builder registry](/form-builder#registry).

Registry dependencies name only other `@offload` items. `shadcn add --overwrite` rewrites every file of every registry dependency, so an item that listed `button` would replace the site's own button on every update. Add the shadcn components that the items import yourself, with `pnpm dlx shadcn@latest add`. The forms import `button`, `checkbox`, `field`, `input`, `spinner`, and `textarea`, the verify-email form only `button` and `spinner`, and the account menu `button` and `dropdown-menu`.

Each item targets one release of `@adirishi/offload-accounts`, and its `meta` names it, such as `"meta": { "@adirishi/offload-accounts": "{{version}}" }`. The registry serves only the items for the latest release. Update the package and add the items again together, with `--overwrite`. The registry doesn't list `@adirishi/offload-accounts`, so the shadcn CLI never changes its version.

The components import their server functions from `@/server/account.functions`, which the site writes. They link to `/login`, `/sign-up`, `/forgot-password`, and `/account` with TanStack Router's typed links, so the site needs those routes, or edited links, to type-check.

`SignUpForm` and `ForgotPasswordForm` render the Turnstile widget with the actions `sign-up` and `forgot-password` when the visitor first focuses or touches the form. The server rejects a token for another action, so keep the actions when you edit the components.
