`/razorpay`, `/mips`, and the main entry point run only on the server. `/client` runs in the browser. `payload`, `@payloadcms/plugin-ecommerce`, and `zod` 4 are peer dependencies. The adapters need Offload's build of `@payloadcms/plugin-ecommerce`, because they settle orders through the export that the [server settlement patch](/patches/ecommerce-server-settlement) adds.

```json package.json
"@adirishi/offload-payments": "{{version}}",
"@payloadcms/plugin-ecommerce": "npm:@adirishi/offload-plugin-ecommerce@{{version}}"
```

[Take payments at checkout](/checkout) sets up a site.

## How an order is settled

Every payment starts at the plugin's `initiate` endpoint and ends in core's settlement: one atomic claim that moves the transaction from `pending` to `processing`, then the order, the cart's `purchasedAt`, the stock decrement, and `succeeded`. Only the request that wins the claim writes anything. A request that loses it, such as a duplicate webhook or a second confirmation, gets the existing order back.

Three things can ask for settlement, and each one is only a notice that a payment may exist:

- the browser, through the plugin's `confirm-order` endpoint;
- the gateway, through Razorpay's webhook or the mIPS payment notification (IMN);
- `reconcilePaymentsTask()`, on the Cron Trigger.

Before it settles, an adapter finds the one transaction that holds the gateway order it stored at `initiate`, and asks the gateway's API for the payment. It settles only when the API reports a paid status, the stored gateway order, and the transaction's amount and currency. The amount comes from the cart's `subtotal`, which the carts collection computes from stored prices. The browser never sends an amount.

A payment that the API reports with another amount or currency is refused, and the adapter writes the reason to the transaction's `lastError`. A failure event doesn't fail the transaction, because a gateway can still complete the payment later. Reconciliation expires a transaction only when no payment can arrive any more.

A logged-in user of the plugin's `customers.slug` collection owns the transaction and the order. Any other logged-in user, such as an admin, checks out as a guest, known by email. The [customers slug patch](/patches/ecommerce-adapter-customers-slug) passes that slug to the adapters.

Settlement assumes the plugin's default slugs for the other collections: `transactions`, `orders`, `carts`, `products`, and `variants`.

## Currencies

`MUR` and `INR` are `Currency` objects for the plugin's `currencies.supportedCurrencies`. Both have 2 decimals, so prices are stored in cents and paise.

| Constant | `code` | `decimals` | `symbol` | `symbolDisplay` |
| -------- | ------ | ---------- | -------- | --------------- |
| `MUR`    | `MUR`  | 2          | `Rs`     | `code`          |
| `INR`    | `INR`  | 2          | `₹`      |                 |

Razorpay takes amounts in the currency's smallest unit, which is what the plugin stores. mIPS takes EUR, GBP, MUR, USD, and ZAR, in decimal units.

## razorpayAdapter()

```ts
razorpayAdapter(options: RazorpayAdapterOptions): OffloadPaymentAdapter
```

| Option           | Type                                   | Description                                                                                      |
| ---------------- | -------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `keyID`          | `string`                               | Required. The key id from the Razorpay Dashboard. The browser receives it from `initiate`.       |
| `keySecret`      | `string`                               | Required. The key secret. It authenticates API calls and verifies Checkout's payment signature.  |
| `webhookSecret`  | `string`                               | Required. The secret of the webhook in the Razorpay Dashboard.                                   |
| `apiURL`         | `string`                               | The API's origin. Defaults to `https://api.razorpay.com`. Change it only to test against a stub. |
| `label`          | `string`                               | The payment method's label in the admin. Defaults to `Razorpay`.                                 |
| `groupOverrides` | `PaymentAdapterArgs["groupOverrides"]` | Overrides the `razorpay` group on transactions, as for the plugin's Stripe adapter.              |

The adapter's name is `razorpay`. Each transaction has a `razorpay` group with `orderID` (unique), `paymentID`, `lastEventID`, `shippingAddress`, and `lastError`.

### Endpoints

| Endpoint                                    | Called by           | What it does                                                                                                                                                                    |
| ------------------------------------------- | ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /api/payments/razorpay/initiate`      | The checkout button | Creates the `pending` transaction and a Razorpay order for the cart's subtotal, with the transaction ID as its `receipt`. Returns `keyID`, `orderID`, `amount`, and `currency`. |
| `POST /api/payments/razorpay/confirm-order` | The checkout button | Takes Checkout's `razorpay_order_id`, `razorpay_payment_id`, and `razorpay_signature`, and settles. Returns `orderID` and `transactionID`.                                      |
| `POST /api/payments/razorpay/webhooks`      | Razorpay            | Settles on `payment.captured`, `payment.authorized`, and `order.paid`. Records `payment.failed`.                                                                                |

`confirm-order` checks, in order:

1. The transaction that holds `razorpay_order_id` belongs to the cart that the request proves access to.
2. The signature is the hex HMAC-SHA256 of `<stored order id>|<payment id>` with the key secret.
3. `GET /v1/payments/:id` reports the stored order, the transaction's amount and currency, and `captured`. An `authorized` payment is captured first.

The webhook endpoint reads the raw body and checks `X-Razorpay-Signature`, the hex HMAC-SHA256 of the body with the webhook secret, in constant time. A missing or wrong signature gets `400`. It then finds the transaction by the order id in the event and asks `GET /v1/orders/:id/payments` for a captured payment. It answers:

- `200` for every verified event it handled or doesn't need, including an event for an order that isn't the site's, an event it already handled (the same `x-razorpay-event-id` as the transaction's `lastEventID`), and a payment that doesn't match;
- `500` when the Razorpay API fails, so Razorpay delivers the event again.

`payment.failed` writes the error to `lastError` and leaves the transaction `pending`. Razorpay can send `payment.captured` for the same payment later, and the transaction still settles.

### Authorized payments

Razorpay captures payments made through an order automatically, unless the account's capture settings say otherwise. Razorpay refunds an `authorized` payment that isn't captured within 3 days. The adapter captures an authorized payment before it settles, in `confirm-order`, in the webhook, and in reconciliation. If the transaction's cart was already bought through another transaction, it doesn't capture, so Razorpay refunds the payment, and it writes the reason to `lastError`.

## mipsAdapter()

```ts
mipsAdapter(options: MipsAdapterOptions): OffloadPaymentAdapter
```

| Option           | Type                                   | Description                                                                                                                                                                                               |
| ---------------- | -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `credentials`    | `object`                               | Required. The credentials from MIPS, described below.                                                                                                                                                     |
| `returnURL`      | `string`                               | Required. The page that the customer returns to after paying, absolute or relative to the site. The adapter adds `?reference=<reference>`. MIPS sends the customer there only after a successful payment. |
| `apiURL`         | `string`                               | The API's base URL. Defaults to `https://api.mips.mu/api`. Change it only to test against a stub.                                                                                                         |
| `label`          | `string`                               | The payment method's label in the admin. Defaults to `Card (mIPS)`.                                                                                                                                       |
| `groupOverrides` | `PaymentAdapterArgs["groupOverrides"]` | Overrides the `mips` group on transactions.                                                                                                                                                               |

| `credentials` key  | MIPS name           | Use                                   |
| ------------------ | ------------------- | ------------------------------------- |
| `username`         | Basic auth user     | Every API call                        |
| `password`         | Basic auth password | Every API call                        |
| `merchantID`       | `id_merchant`       | The `authentify` object of every call |
| `entityID`         | `id_entity`         | The `authentify` object of every call |
| `operatorID`       | `id_operator`       | The `authentify` object of every call |
| `operatorPassword` | `operator_password` | The `authentify` object of every call |
| `salt`             | `salt`              | `decrypt_imn_data`                    |
| `cipherKey`        | `cipher_key`        | `decrypt_imn_data`                    |

The adapter's name is `mips`. Each transaction has a `mips` group with `reference` (unique), `paymentMethod`, `shippingAddress`, and `lastError`. `reference` is the 20-character alphanumeric `id_order` that MIPS knows the payment by.

### Endpoints

| Endpoint                                | Called by        | What it does                                                                                                                               |
| --------------------------------------- | ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `POST /api/payments/mips/initiate`      | The payment zone | Creates the `pending` transaction and calls `load_payment_zone`. Returns `reference` and `paymentZone`, the HTML of MIPS's payment iframe. |
| `POST /api/payments/mips/confirm-order` | The return page  | Takes `reference`, and settles. Returns `orderID` and `transactionID`.                                                                     |
| `POST /api/payments/mips/imn`           | MIPS             | Takes the encrypted IMN, settles, and answers `success` or `fail` as plain text.                                                           |

The IMN carries no signature that the site can check, and anyone who captured one can send it again. So the endpoint treats it only as a notice. It asks `decrypt_imn_data` to decrypt it, which proves only that MIPS encrypted it for this merchant, and uses only its `id_order`. Then it asks `orders_management` for `get_order_all_data` and settles only when that order is `success` with the transaction's amount and currency. `confirm-order` runs the same lookup. Neither uses the amount in the IMN.

## reconcilePaymentsTask()

```ts
reconcilePaymentsTask(options: ReconcilePaymentsOptions): TaskConfig
```

| Option     | Type                      | Description                                                                         |
| ---------- | ------------------------- | ----------------------------------------------------------------------------------- |
| `adapters` | `OffloadPaymentAdapter[]` | Required. The adapters whose transactions to reconcile.                             |
| `schedule` | `ScheduleConfig[]`        | When Payload queues the task. Defaults to every ten minutes on the `default` queue. |

A Payload job task with the slug `reconcilePayments`. Add it to `jobs.tasks`. `createPayloadWorker()` queues and runs scheduled jobs on each Cron Trigger, so the Worker needs a Cron Trigger at least as frequent as `schedule`.

Each run does two things:

1. It repairs transactions that settlement left in `processing` for 15 minutes. On D1, which has no database transactions, a Worker that stops during settlement leaves them there. If an order took the transaction, the task marks it `succeeded` and logs an error, because the stock decrement may not have run. If no order took it, settlement had written nothing else, so the task returns it to `pending`.
2. It asks the adapters about 50 `pending` transactions, the ones it checked least recently first. A transaction that stays pending moves to the back.

| Gateway  | Settles when                                   | Expires when                                                                                                                                                                                                                  |
| -------- | ---------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Razorpay | The order has a captured or authorized payment | No payment is captured or authorized 3 days and 1 hour after the order's last payment attempt, or after `initiate` if there was none. A transaction whose `initiate` failed before it created an order expires after an hour. |
| mIPS     | `get_order_all_data` reports `success`         | MIPS reports the order `expired`, or the order isn't paid 24 hours after `initiate`                                                                                                                                           |

## Client adapters

`razorpayAdapterClient()` and `mipsAdapterClient()` return the `paymentMethods` entries for the plugin's `EcommerceProvider`. Each takes an optional `label`. `/client` also exports `MUR` and `INR`, so browser code doesn't import the main entry point.

## Registry

The checkout UI installs from Offload's shadcn registry, from [`packages/payments/registry.json`](https://github.com/AdiRishi/offload-cms/blob/main/packages/payments/registry.json).

| Item                 | Installs                                     | Uses the shadcn components | Registry dependencies        | npm dependencies |
| -------------------- | -------------------------------------------- | -------------------------- | ---------------------------- | ---------------- |
| `razorpay-checkout`  | `components/payments/razorpay-checkout.tsx`  | `button`, `spinner`        | None                         | `zod`            |
| `mips-payment-zone`  | `components/payments/mips-payment-zone.tsx`  | `button`, `spinner`        | None                         | `zod`            |
| `mips-confirm-order` | `components/payments/mips-confirm-order.tsx` | `spinner`                  | `@offload/mips-payment-zone` | `zod`            |

The items don't install the shadcn components they use, so `--overwrite` never replaces the site's copies. Add the ones the site lacks with `shadcn add`, without `--overwrite`.

Each item's `meta` names the release of `@adirishi/offload-payments` it was built for. The components call the plugin's `usePayments()`, so they render inside `EcommerceProvider`.

### RazorpayCheckout

```tsx
<RazorpayCheckout customerEmail={email} onConfirmed={({ orderID }) => navigate(orderID)} />
```

A button that loads `https://checkout.razorpay.com/v1/checkout.js` on its first click, calls `initiate`, and opens Checkout for the Razorpay order. When Checkout reports a payment, it calls `confirm-order` with Checkout's response and calls `onConfirmed` with the order. Pass `customerEmail` for a guest. A logged-in customer pays as their account. `name` sets the name that Checkout shows.

### MipsPaymentZone

```tsx
<MipsPaymentZone customerEmail={email} />
```

A button that calls `initiate` and replaces itself with the payment zone that MIPS returns. It inserts the zone's HTML so that its script runs, which `innerHTML` wouldn't do. It keeps a guest's email in `sessionStorage` under the reference, for the return page.

### MipsConfirmOrder

```tsx
<MipsConfirmOrder reference={reference} onConfirmed={({ orderID }) => navigate(orderID)} />
```

Renders on the page at the adapter's `returnURL`, with the `reference` from the page's query string. It waits for the provider's cart, then calls `confirm-order` once with the reference and the guest's stored email, and calls `onConfirmed` with the order. If the IMN settled the order first, `confirm-order` returns that order. While it confirms, it shows a spinner. If the confirmation fails, it says that a paid order will still be confirmed, which the IMN and reconciliation do.
