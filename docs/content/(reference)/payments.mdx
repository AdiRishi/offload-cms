`/client` runs in the browser and also exports `MUR` and `INR`, so browser code never imports the main entry point. The main entry point, `/razorpay`, and `/mips` run only on the server. The adapters need Offload's build of `@payloadcms/plugin-ecommerce`, because they settle orders through the export that the [server settlement patch](/patches/ecommerce-server-settlement) adds. [Take payments at checkout](/checkout) sets up a site.

## How an order is settled

Every payment starts at the plugin's `initiate` endpoint and ends in core's settlement. Settlement makes one atomic claim that moves the transaction from `pending` to `processing`, then writes the order, the cart's `purchasedAt`, the stock decrement, and `succeeded`. Only the request that wins the claim writes anything. A request that loses it, such as a duplicate webhook, gets the existing order back. A `confirm-order` that loses the claim to a settlement that hasn't finished answers `409` with `{ status: "processing" }`, and the registry components confirm again.

Three things can ask for settlement, and each one is only a notice that a payment may exist:

- the browser, through the plugin's `confirm-order` endpoint;
- the gateway, through Razorpay's webhook or the mIPS payment notification (IMN);
- `reconcilePaymentsTask()`, on the Cron Trigger.

Before it settles, an adapter finds the one transaction that holds the gateway order it stored at `initiate`, and asks the gateway's API for the payment. It settles only when the API reports a paid status, the stored gateway order, and the transaction's amount and currency. The amount comes from the cart's `subtotal`, which `initiate` checks against current prices. The browser never sends an amount.

The transaction copies the cart's items with the properties that a site's `cartItemMatcher` adds, as the Stripe adapter's does, and the order copies them from the transaction. Each item drops the cart row's `id`, because another checkout of the same cart reuses it.

A paid payment never settles when:

- its amount or currency differs from the transaction's;
- another transaction already bought the cart. The customer paid twice, so the adapter doesn't create a second order and doesn't capture an authorized payment;
- its transaction failed or was cancelled.

The adapter then writes the reason, with the payment's ID, to the transaction's `lastError`, and logs it at error level. An admin refunds the payment from the gateway's dashboard. Inside `confirm-order`, the adapter ends core's database transaction before that write, so the flag stays on Postgres as on D1. Two payments for one cart that settle at the same moment can't both create an order, because core gives each order the cart's unique `cartKey`. The second insert fails, and the adapter flags that payment the same way. Core's `confirm-order` answers that error with `409` and `{ status: "cart_already_purchased" }` when an adapter passes it through, as Stripe's does. Offload's adapters flag the payment instead, so their `confirm-order` answers `500`.

A payment for a transaction that reconciliation expired reopens it and settles, when the cart is still open. A failure event never fails the transaction, because the gateway can still complete the payment. Reconciliation expires a transaction only when no payment can arrive any more.

A logged-in user of the plugin's `customers.slug` collection owns the transaction and the order. Any other logged-in user, such as an admin, checks out as a guest, known by email. The [customers slug patch](/patches/ecommerce-adapter-customers-slug) passes that slug and the currencies to the adapters. Settlement uses the plugin's slugs for every collection, including a `slugMap`. Each write sets only the transaction fields that its path owns, and a write for a pending transaction applies only while it is still pending, so a late event can't undo a settlement. That relies on the SQL database adapters, D1 and Postgres, which write only the columns they're given.

## Currencies

The plugin stores prices in units of `10 ** decimals` of the configured currency. Razorpay takes the currency's smallest ISO 4217 unit, so its `initiate` refuses a currency whose configured `decimals` isn't the ISO exponent. mIPS takes EUR, GBP, MUR, USD, and ZAR in decimal units, at least 1.00. Its `initiate` refuses any other currency, a currency configured with more than 2 decimals, and a subtotal below 1.00.

## razorpayAdapter()

Each transaction has a `razorpay` group with `orderID` (unique), `paymentID`, `lastEventID`, `shippingAddress`, and `lastError`.

### Endpoints

The adapter adds three endpoints under `/api/payments/razorpay`:

- `initiate` creates the `pending` transaction and a Razorpay order for its amount, with the transaction's ID in the order's `notes`. The order's `receipt` stays unique when several databases, such as staging and production, share the keys. It returns Checkout's `timeout` of 15 minutes, which also bounds when reconciliation may expire an order with no payment attempt.
- `confirm-order` takes the `razorpay_order_id`, `razorpay_payment_id`, and `razorpay_signature` that Checkout's handler receives.
- `webhooks` takes Razorpay's events. It settles on `payment.captured`, `payment.authorized`, and `order.paid`, and records `payment.failed`.

`confirm-order` checks, in order:

1. The transaction that holds `razorpay_order_id` belongs to the cart that the request proves access to.
2. The signature is the hex HMAC-SHA256 of `<stored order id>|<payment id>` with the key secret. The adapter uses the order ID that it stored, not the one the browser sent.
3. `GET /v1/payments/:id` reports the stored order, the transaction's amount and currency, and `captured`. An `authorized` payment of a pending transaction is captured first.

It answers with `orderID`, `transactionID`, and the order's `accessToken` when the site's orders collection has that field, as the Stripe adapter does. Payload's ecommerce template adds one so that guests can look up their orders.

The webhook endpoint reads the raw body and checks `X-Razorpay-Signature`, the hex HMAC-SHA256 of the body with the webhook secret, in constant time. A missing or wrong signature gets `400`. Razorpay retries any other answer that isn't `2xx` for 24 hours and then disables the webhook. So the endpoint answers `500` only when a retry may help, such as for a failed database query, and `200` for the rest:

- an event it can't read is logged at error level;
- an event for an order that isn't the site's needs nothing. So does an event it already handled (the same `x-razorpay-event-id` as the transaction's `lastEventID`), an event for a transaction that a settlement holds in `processing`, and an event for the payment that already settled the transaction;
- `payment.failed` writes the error to `lastError` and leaves the transaction `pending`, because Razorpay can still capture the payment;
- a paid event is answered at once and settled afterwards with `waitUntil()` from `@adirishi/offload-cloudflare`, because Razorpay waits only 5 seconds and settlement on D1 can take longer. The adapter asks `GET /v1/payments/:id` for the event's payment. If that work fails, reconciliation settles the pending transaction later.

The `webhooks` handlers run for every event the endpoint can read, before the duplicate check, and before the endpoint answers. Razorpay sends an event again after a timeout or a `500`, so a handler can receive the same event more than once, and the event's `x-razorpay-event-id` header identifies it. A handler that throws also stops the adapter's own handling of that event until Razorpay's retry. Keep handlers within Razorpay's 5 seconds, or pass slow work to `waitUntil()`.

Every Razorpay API call times out after 8 seconds.

### Authorized payments

Razorpay captures payments made through an order automatically, unless the account's capture settings say otherwise, so the adapter rarely sees an authorized payment. Razorpay refunds an `authorized` payment that isn't captured within 3 days. When the adapter does see one, it captures it before settling, but only for a `pending` transaction whose cart no other transaction bought. Otherwise it leaves the payment for Razorpay to refund, and writes the reason to `lastError`.

## mipsAdapter()

Each transaction has a `mips` group with `reference` (unique), `decimals`, `paymentMethod`, `shippingAddress`, and `lastError`. `reference` is the `id_order` that MIPS knows the payment by, 20 random alphanumeric characters. `decimals` keeps the currency's configured decimals from `initiate`, so a later change to the currency config doesn't change the amounts that the lookups send.

### Endpoints

The adapter adds three endpoints under `/api/payments/mips`:

- `initiate` creates the `pending` transaction and calls `load_payment_zone`. It returns `reference` and `paymentZone`, the HTML of MIPS's payment iframe. If MIPS refuses, the transaction expires at once, because the customer never saw a payment zone.
- `confirm-order` takes `reference`, checks that its transaction belongs to the request's cart, and settles.
- `imn` takes the encrypted IMN, settles, and answers `success` or `fail` as plain text.

The IMN carries no signature that the site can check, and anyone who captured one can send it again. So the endpoint treats it only as a notice:

1. It applies the rate limit, keyed by the `cf-connecting-ip` header (`429`), and refuses a body over 16 KiB (`413`).
2. It asks `decrypt_imn_data` to decrypt the message, which proves only that MIPS encrypted it for this merchant, and uses only its `id_order`. A body without `crypted_callback`, or an explicit refusal from MIPS, gets `400 fail`.
3. It asks `orders_management` for `get_order_all_data`, and settles only when that order is `success` with the transaction's amount and currency. `confirm-order` runs the same lookup. Neither uses the amount in the IMN.

It answers `200 success` when the transaction is settled, and `200 fail` when the payment can't settle or the order isn't the site's. It answers `500 fail` for anything MIPS should retry: a decrypt or lookup that fails, or an order still `waiting`. It settles before it answers, so `success` is true, and passes the settlement to `waitUntil()` so a dropped connection can't stop it halfway. Every mIPS API call times out after 8 seconds.

The documents disagree on whether `get_order_all_data` reports decimal units or cents. The adapter accepts either, and logs at warning level which one matched, until MIPS confirms.

If MIPS publishes the IPs it sends the IMN from, allow only those for `/api/payments/mips/imn` with a WAF rule.

## reconcilePaymentsTask()

The task's slug is `reconcilePayments`. Runs that overlap are safe, because every change is a conditional transition.

Each run does two things:

1. It repairs transactions that settlement left in `processing` for 15 minutes. On D1, which has no database transactions, a Worker that stops during settlement leaves them there. Settlement writes the transaction's ID to the order's `settlementKey` in the order's first insert. If such an order exists, the task links it, marks the transaction `succeeded`, and logs an error, because the stock decrement may not have run. If none exists, settlement had written nothing else, so the task returns the transaction to `pending`.
2. It asks the adapters about `batchSize` `pending` transactions, the ones it checked least recently first. A transaction that stays pending, or whose check fails, moves to the back, so transactions that wait out a gateway's payment window can't fill every batch. A failure goes to the transaction's `lastError` and the error log.

The job's output counts the transactions it `checked`, `settled`, `expired`, left `pending`, and `failed`, so a run where every check failed shows in `payload-jobs`.

| Gateway  | Settles when                                   | Expires when                                                                                                                                                                                                                                            |
| -------- | ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Razorpay | The order has a captured or authorized payment | The order has no payment attempt 1 hour after Checkout's 15-minute timeout. With attempts, no payment is captured or authorized 3 days and 1 hour after the last one. Razorpay has no record of the order (`404`), which happens after the keys change. |
| mIPS     | `get_order_all_data` reports `success`         | MIPS reports the order `expired` or `cancelled`. An order still unpaid 24 hours after `initiate` is cancelled with `cancel_order` first, and expires only if MIPS then reports it closed.                                                               |

Each checked transaction costs a few gateway calls and database queries. On Workers Paid, a Cron Trigger invocation can make 10,000 subrequests, and D1 queries count, so the default batch of 50 fits. On Workers Free it can make 50 to the internet and 1,000 to Cloudflare services, so set `batchSize` to about 15.

## Registry

The checkout UI installs from Offload's shadcn registry, from [`packages/payments/registry.json`](https://github.com/AdiRishi/offload-cms/blob/main/packages/payments/registry.json), into `components/payments/`. `mips-confirm-order` installs `mips-payment-zone` too, because it reads the guest's email that the payment zone stores.

The items use the shadcn `button` and `spinner` but don't install them, so `--overwrite` never replaces the site's copies. Add the ones the site lacks with `shadcn add`, without `--overwrite`.

Each item's `meta` names the release of `@adirishi/offload-payments` it was built for. The components use only browser APIs in Vite's default build target, Baseline Widely Available, which includes Safari 16. The components call the plugin's `usePayments()`, so they render inside `EcommerceProvider`.

### RazorpayCheckout

A button that loads `https://checkout.razorpay.com/v1/checkout.js` on its first click, calls `initiate`, and opens Checkout for the Razorpay order with the `timeout` that `initiate` returns. When Checkout reports a payment, the button stays disabled for good, and it calls `confirm-order` up to 6 times over about 20 seconds, then calls `onConfirmed` with the order. If every attempt fails, it says that the payment was received and the order will be confirmed, and not to pay again. If `initiate` fails, for example because prices changed, it refreshes the cart and shows the endpoint's message.

### MipsPaymentZone

A button that calls `initiate` and replaces itself with the payment zone that MIPS returns. It parses the zone's HTML without running it, and builds only the `<script src>` and `<iframe src>` elements whose origin is in `origins`. Inline scripts and every other element are dropped, and a zone without a trusted iframe counts as a failed start. It keeps a guest's email in `sessionStorage` under the reference, for the return page.

MIPS's script runs in the site's origin, which also serves `/admin` and `/api`, so the site trusts MIPS as it trusts Razorpay's `checkout.js`. A sandboxed `srcdoc` frame can't isolate it. The payment frame inside inherits the sandbox and breaks, and `allow-same-origin` would give the frame the site's origin.

### MipsConfirmOrder

Renders on the page at the adapter's `returnURL`, with the `reference` from the page's query string. It waits for the provider's cart, then calls `confirm-order` with the reference and calls `onConfirmed` with the order. It tries up to 6 times over about 20 seconds, because the IMN may be settling the same payment, and sends a guest's email from this tab's `sessionStorage` when it has one. Without a cart after 5 seconds, or when every attempt fails, it says that a paid order will be confirmed by email and not to pay again. The IMN and reconciliation confirm it.
