## offloadVite()

```ts
offloadVite(options: OffloadViteOptions): UserConfigFnPromise
```

Returns the site's Vite config: Payload's `withPayload()` with TanStack Start, React Server Components, and React. `vite build` and `vite preview` target workerd through `@cloudflare/vite-plugin`. `vite dev` runs in Node, because the RSC module runner can't load Payload's CommonJS dependencies in workerd.

| Option                      | Type                              | Description                                                                                                    |
| --------------------------- | --------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `payloadConfigPath`         | `string`                          | Required. The path to `payload.config.ts`.                                                                     |
| `vite`                      | `(env: ConfigEnv) => UserConfig`  | The site's own Vite config, merged over Offload's. Its plugins run after Offload's.                            |
| `pluginsBefore`             | `PluginOption[]`                  | Plugins that run before Payload's, TanStack Start's, and Offload's own, among plugins with the same `enforce`. |
| `cloudflare`                | `@cloudflare/vite-plugin` options | Passed to the Cloudflare plugin. Offload sets `viteEnvironment`.                                               |
| `devServerExternalPackages` | `string[]`                        | CommonJS packages that `vite dev` leaves to Node, in addition to `prompts`, which Offload adds.                |

Put a plugin in `pluginsBefore` when it must see the source before any other transform. TanStack's `devtools()` from `@tanstack/devtools-vite` is one. It writes each element's source line into a `data-tsd-source` attribute. After another plugin has changed the file, the server and the client write different lines, and React reports a hydration mismatch.

Vite orders plugins by `enforce` before their order in the array, and Offload's own transforms use `enforce: "pre"`. A plugin in `pluginsBefore` without `enforce: "pre"` still runs after them. `devtools()` sets `enforce: "pre"`.

```ts vite.config.ts
offloadVite({
  payloadConfigPath: path.resolve(import.meta.dirname, "src/payload.config.ts"),
  pluginsBefore: [devtools()],
  vite: () => ({ plugins: [tailwindcss()] }),
});
```

### Payload package check

Every Payload package in the site must be the Offload build at the same version as `@adirishi/offload-cloudflare`.

- When `vite dev` or `vite build` starts, `offloadVite()` reads each `payload` and `@payloadcms/*` dependency in the site's `package.json`. It throws if one is Payload's own build or a different Offload release.
- At the end of `vite build`, it fails the build if any bundled module comes from Payload's own build of a package, including one that another dependency installed.

Each error names the package and the line to install, such as `"@payloadcms/plugin-seo": "npm:@adirishi/offload-plugin-seo@{{version}}"`. Put the line in the site's dependencies, or in the package manager's overrides when another dependency installs the package.

### Changes to the workerd build

For `vite build` and `vite preview`, `offloadVite()` changes Payload's Node-oriented build in these ways:

| Change                                                             | Without it                                                                                       |
| ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------ |
| Removes the Node externals that `withPayload()` sets               | The bundle imports packages from `node_modules`, which a Worker doesn't have.                    |
| Removes the `browser` resolve condition from server environments   | workerd resolves `payload` to its client-only entry.                                             |
| Replaces `import.meta.url` with a placeholder when it is undefined | Payload fails at module scope, where it derives a directory from `import.meta.url`.              |
| Makes the adapter's hidden GraphQL imports literal                 | The GraphQL handler can't load, because the bundler never saw its imports.                       |
| Resolves every server import of `graphql` to its ESM build         | Two copies of `graphql` load, and every query with arguments fails with "Unexpected input type". |
| Resolves `pg-pool` to its CommonJS build                           | The Worker fails at startup with `Class extends value #<Object> is not a constructor`.           |
| Imports `@cloudflare/vite-plugin` only for build and preview       | Loading the plugin breaks CommonJS interop in Node-mode dev.                                     |

[`packages/cloudflare/src/vite.ts`](https://github.com/AdiRishi/offload-cms/blob/main/packages/cloudflare/src/vite.ts) and [`workerd-transforms.ts`](https://github.com/AdiRishi/offload-cms/blob/main/packages/cloudflare/src/workerd-transforms.ts) have one Vite plugin per change. The plugins that rewrite code return sourcemaps, so stack traces point at the original lines.

## getBindings()

```ts
getBindings(): Promise<Cloudflare.Env>
```

Returns the Worker's bindings. In workerd, the bindings come from `cloudflare:workers`. In Node, for `vite dev` and the Payload CLI, they come from Wrangler's `getPlatformProxy()`, which reads the same local D1 and R2 state as `vite preview`. `CLOUDFLARE_ENV` selects the Wrangler environment.

Call it with top-level `await` in `payload.config.ts`, and in a server function that reads a binding or secret when it runs. In Node, it throws if the site doesn't have `wrangler` installed.

In Node, the first call for a Wrangler environment starts a platform proxy, and every later call in the process returns its bindings. `vite dev` reloads the Payload config after each edit and keeps the proxy, so restart `vite dev` after you change `wrangler.jsonc` or `.dev.vars`.

To keep test data apart from development data, give the tests their own Wrangler environment with a different D1 `database_id` and R2 bucket, and run the Payload CLI, the build, and the tests with `CLOUDFLARE_ENV` set to it. Wrangler keeps local state per database and bucket, so the two sets of data never mix. [Keep test data apart](/test) shows the setup.

## hyperdrivePoolConfig()

```ts
hyperdrivePoolConfig(hyperdrive: Hyperdrive, options?: PoolConfig): PoolConfig
```

Returns the `pool` option for `postgresAdapter()`. The returned config reads `hyperdrive.connectionString` when the pool connects, because a Worker can read it only inside a request. It sets `maxUses: 1`, so each query gets a new connection and Hyperdrive does the pooling. It also sets `max: Infinity`, so a request never waits for a connection that another request releases: pg-pool would open that connection inside the other request, and workerd cancels a request that uses another request's I/O. Values in `options` override these.

## createPayloadWorker()

```ts
createPayloadWorker(args: {
  handler: { fetch: (request: Request) => Response | Promise<Response> };
  jobs?: RunOptions;
}): ExportedHandler
```

Returns the Worker's default export.

| Argument  | Description                                                                                                    |
| --------- | -------------------------------------------------------------------------------------------------------------- |
| `handler` | The default export of `@tanstack/react-start/server-entry`. It serves every request.                           |
| `jobs`    | Options for `payload.jobs.run()`, except `req`. The defaults are `allQueues: true` and `overrideAccess: true`. |

On each Cron Trigger, the Worker queues Payload's scheduled jobs with `payload.jobs.handleSchedules()`, then runs the due jobs with `payload.jobs.run()`. Scheduled publishing runs this way.

## Where Payload runs

TanStack Start builds the Worker as two environments. The RSC environment runs server functions and renders the admin. The SSR environment runs the Worker entry and server routes, and renders HTML. Code in either one that imports `@payload-config` or `payload` bundles its own copy of Payload. In the `e2e` site, the second copy added 1,117 KiB to the compressed Worker.

The Worker entry and the API route handlers below load Payload from the RSC environment with `import.meta.viteRsc.import()` from `@vitejs/plugin-rsc`, so the Worker bundles one copy. A server route of your own that imports `payload` or `@payload-config` brings the second copy back. Read content in a `createServerFn()` handler instead. It runs in the RSC environment, also when a route loader or a server route calls it.

## payloadApiHandlers()

```ts
payloadApiHandlers(): { DELETE; GET; OPTIONS; PATCH; POST; PUT }
```

Returns the server handlers for the REST route at `/_payload/api/$`. Use it in place of `payloadApiHandlers()` from `@payloadcms/tanstack-start/server`, which Payload's TanStack Start template uses and which imports Payload into the SSR environment.

```ts src/app/_payload/api.$.ts
import { payloadApiHandlers } from "@adirishi/offload-cloudflare/routes";
import { createFileRoute } from "@tanstack/react-router";

export const Route = createFileRoute("/_payload/api/$")({
  server: {
    handlers: payloadApiHandlers(),
  },
});
```

## payloadGraphQLHandlers()

```ts
payloadGraphQLHandlers(): { POST }
```

Returns the server handlers for a TanStack Start route at `/_payload/api/graphql`. Payload's TanStack Start template routes only REST.

```ts src/app/_payload/api.graphql.ts
import { payloadGraphQLHandlers } from "@adirishi/offload-cloudflare/routes";
import { createFileRoute } from "@tanstack/react-router";

export const Route = createFileRoute("/_payload/api/graphql")({
  server: {
    handlers: payloadGraphQLHandlers(),
  },
});
```
