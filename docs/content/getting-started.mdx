title: Getting started
description: Create a TanStack Start site that runs Payload as a Cloudflare Worker on D1, R2, and Cloudflare Images, and run it locally.

This guide creates a site whose Worker serves your frontend, the Payload admin at `/admin`, and Payload's API, with content in D1, uploads in R2, and image variants from Cloudflare Images. At the end, the admin runs locally with a user you can log in as.

You need Node 24 and pnpm. To deploy, you also need a Cloudflare account on the Workers Paid plan, because a Payload Worker is larger than the free plan's 3 MB limit.

<Steps>
  <Step title="Connect to GitHub Packages">
    Offload is on GitHub Packages, which needs a token even for public packages. Create a classic GitHub token with the `read:packages` scope. The GitHub CLI's token works once it has that scope: run `gh auth refresh --scopes read:packages`, then use `gh auth token`.

    The site's `.npmrc`, which the template includes, points the `@adirishi` scope at GitHub Packages:

    ```ini .npmrc
    @adirishi:registry=https://npm.pkg.github.com
    ```

    Keep the token out of this file. It's committed, and pnpm 11.5.3 and later don't expand `${...}` in a project `.npmrc`'s registry credentials ([GHSA-3qhv-2rgh-x77r](https://github.com/advisories/GHSA-3qhv-2rgh-x77r)). Give pnpm the token in one of these ways:

    - Save it in your user config, once per machine: `pnpm config set "//npm.pkg.github.com/:_authToken" <token>`.
    - Pass it to one command in pnpm's environment form: `env "pnpm_config_//npm.pkg.github.com/:_authToken=$(gh auth token)" pnpm install`.

    In GitHub Actions, `actions/setup-node` writes a user-level `.npmrc` that reads `NODE_AUTH_TOKEN`:

    ```yaml .github/workflows/ci.yml
    - uses: actions/setup-node@v7
      with:
        registry-url: https://npm.pkg.github.com
        scope: "@adirishi"
    - run: pnpm install --frozen-lockfile
      env:
        NODE_AUTH_TOKEN: ${{ secrets.OFFLOAD_PACKAGES_TOKEN }}
    ```

    A workflow's `GITHUB_TOKEN` can install only the packages that grant its repository read access, and Offload's packages belong to another account. Store a classic token with `read:packages` as a repository secret, `OFFLOAD_PACKAGES_TOKEN` in this example.

  </Step>
  <Step title="Create the site">
    `pnpm create @adirishi/offload` copies Offload's site template into a new directory and pins it to the latest release. The project's `.npmrc` doesn't exist yet, so pass the registry for this one command:

    ```bash
    pnpm --config.@adirishi:registry=https://npm.pkg.github.com create @adirishi/offload my-site
    ```

    The template is Payload's [`blank-tanstack`](https://github.com/payloadcms/payload/tree/main/templates/blank-tanstack) template with the changes that [the next section](#what-the-template-changes) lists. The directory's name becomes the Worker's name and the name of its D1 database and R2 bucket.

  </Step>
  <Step title="Start the site">
    ```bash
    cd my-site
    cp .dev.vars.example .dev.vars
    pnpm install
    pnpm cf-typegen
    pnpm migrate:regenerate
    pnpm admin:dev
    pnpm dev
    ```

    `.dev.vars` holds the local secrets, including `PAYLOAD_SECRET` and the admin that `pnpm admin:dev` creates. `pnpm cf-typegen` writes the `Env` type for the bindings in `wrangler.jsonc`. `pnpm migrate:regenerate` creates the first migration and applies it to an empty local D1 database.

    Open `/admin` on the address that Vite prints, and log in with `DEV_ADMIN_EMAIL` and `DEV_ADMIN_PASSWORD` from `.dev.vars`.

  </Step>
  <Step title="Run the Worker build">
    `pnpm dev` runs in Node. To run the bundle that Cloudflare runs, build it and serve it in local workerd:

    ```bash
    pnpm build
    pnpm preview
    ```

    The preview uses the same local D1 and R2 state as `pnpm dev`, so the same admin can log in. Local workerd doesn't enforce the deployed Worker's PBKDF2 limit, so this login doesn't show whether a deployed Worker accepts the password hash.

    The preview runs the last build, with the secrets that the build copied from `.dev.vars`. After you change `.dev.vars`, build again before you preview.

  </Step>
</Steps>

## What the template changes

These are the differences between the template and Payload's `blank-tanstack`. To add Offload to a project made from `blank-tanstack`, make the same changes.

- **Packages.** Each Payload package is installed under its upstream name as an alias of its Offload build, at one version, such as `"payload": "npm:@adirishi/offload-payload@{{version}}"`. Code keeps importing `payload` and `@payloadcms/*`. Add every Payload plugin the same way, such as `@payloadcms/plugin-seo` as `npm:@adirishi/offload-plugin-seo@{{version}}`: Payload's dev server throws when its packages' versions differ, and `offloadVite()` stops when it finds an upstream build. The template drops `@payloadcms/db-mongodb` and `@payloadcms/plugin-mcp`, and adds `@payloadcms/db-d1-sqlite`, `@payloadcms/storage-r2`, `@payloadcms/transformer-cloudflare`, `@adirishi/offload-cloudflare`, and `@adirishi/offload-tanstack`.
- **`.npmrc` and `pnpm-workspace.yaml`.** The `@adirishi` scope installs from GitHub Packages. pnpm 11 exempts it from the minimum release age, so a release installs on the day it's published, and runs the install scripts of `workerd` and `esbuild`.
- **`vite.config.ts`.** `offloadVite()` from `@adirishi/offload-cloudflare/vite` replaces `withPayload()`. It builds for workerd and runs `vite dev` in Node. [The reference](/cloudflare#offloadvite) explains what it changes.
- **`wrangler.jsonc`.** D1, R2, and Images bindings, a Cron Trigger every five minutes for Payload's jobs, and a `production` environment for [Deploy to Cloudflare](/deploy).
- **`src/payload.config.ts`.** `getBindings()` supplies the D1 database, the R2 bucket, the Images binding, and `PAYLOAD_SECRET`, from the runtime in workerd and from Wrangler's local state in Node. `push: false` makes migrations the only way the schema changes. The Cloudflare Images transformer makes four variants of each upload. The template keeps `Users` and `Media`, and drops `Folders` and `Tags`.
- **`src/app/_payload/api.$.ts` and `api.graphql.ts`.** REST and GraphQL use `payloadApiHandlers()` and `payloadGraphQLHandlers()` from `@adirishi/offload-cloudflare/routes`, which keep the Worker to [one copy of Payload](/cloudflare#where-payload-runs).
- **`src/server.ts`.** `createPayloadWorker()` is the Worker entry. It serves TanStack Start and runs Payload's jobs on each Cron Trigger.
- **`src/start.ts`.** [`hideServerErrors`](/tanstack#hideservererrors) keeps Payload's SQL out of the browser's error messages, with TanStack Start's CSRF check.
- **`package.json` scripts.** `migrate:regenerate` rewrites the one `initial` migration and resets local D1, `db:reset` empties local D1 and migrates it, `admin:dev` creates the local admin from `.dev.vars`, and `deploy` migrates, builds, and deploys the `production` environment. The template has no tests, Docker files, or ESLint config.
- **`.github/workflows/ci.yml`.** CI installs from GitHub Packages with `OFFLOAD_PACKAGES_TOKEN`, a repository secret with a classic token that has `read:packages`, then type-checks and builds. A workflow's `GITHUB_TOKEN` can't read packages that belong to another account.
- **`.gitignore`.** It ignores `.wrangler`, the generated `worker-configuration.d.ts`, `.dev.vars`, and the `.dev.vars.<environment>` files that the Payload CLI reads in another environment.

## Set up your coding agent

`@adirishi/offload-cloudflare` ships an agent skill that explains what Offload changes about Payload, and points to the skill that the `payload` package ships for everything else. The template's `AGENTS.md` starts with this line. Add it to the `AGENTS.md` of a site made another way:

```md AGENTS.md
For Payload work in this site, read `node_modules/@adirishi/offload-cloudflare/skills/offload/SKILL.md` first.
```

pnpm 12.11 and later can also link the skills that dependencies ship into the agent skill directories a project has, such as `.claude/skills`. After an install, pnpm lists `@adirishi/offload-cloudflare` and `@adirishi/offload-payload` as awaiting approval. Run `pnpm approve` and approve both. The first links Offload's `offload` skill, and the second links Payload's `payload` skill, which the Offload skill builds on. pnpm records the approval in `pnpm-workspace.yaml`, and each link points at the installed version, so the skills change when you update Offload.

Keep the `AGENTS.md` line too. It works with every package manager and agent, and it makes the agent read Offload's skill before Payload's, whose Next.js advice Offload's skill overrides.
