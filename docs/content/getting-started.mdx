---
title: Getting started
description: Set up a TanStack Start site that runs Payload as a Cloudflare Worker on D1 and R2, and run it locally.
---

This guide sets up a site whose Worker serves your frontend, the Payload admin at `/admin`, and Payload's API, with content in D1 and uploads in R2. At the end, the admin runs locally and you can create your first user.

[`e2e`](https://github.com/AdiRishi/offload-cms/tree/main/e2e) in the repository is a complete site built this way. Copy files from it when a step says so.

You need Node 24 and pnpm. To deploy, you also need a Cloudflare account on the Workers Paid plan, because a Payload Worker is larger than the free plan's 3 MB limit.

<Steps>
  <Step title="Connect to GitHub Packages">
    Offload is on GitHub Packages, which needs a token even for public packages. Create a classic GitHub token with the `read:packages` scope. The GitHub CLI's token works once it has that scope: run `gh auth refresh --scopes read:packages`, then use `gh auth token`.

    Point the `@adirishi` scope at GitHub Packages in the site's `.npmrc`:

    ```ini .npmrc
    @adirishi:registry=https://npm.pkg.github.com
    ```

    Keep the token out of this file. It's committed, and pnpm 11.5.3 and later don't expand `${...}` in a project `.npmrc`'s registry credentials ([GHSA-3qhv-2rgh-x77r](https://github.com/advisories/GHSA-3qhv-2rgh-x77r)). Give pnpm the token in one of these ways:

    - Save it in your user config, once per machine: `pnpm config set "//npm.pkg.github.com/:_authToken" <token>`.
    - Pass it to one command in pnpm's environment form: `env "pnpm_config_//npm.pkg.github.com/:_authToken=$(gh auth token)" pnpm install`.

    In GitHub Actions, `actions/setup-node` writes a user-level `.npmrc` that reads `NODE_AUTH_TOKEN`:

    ```yaml .github/workflows/ci.yml
    - uses: actions/setup-node@v7
      with:
        registry-url: https://npm.pkg.github.com
        scope: "@adirishi"
    - run: pnpm install --frozen-lockfile
      env:
        NODE_AUTH_TOKEN: ${{ secrets.OFFLOAD_PACKAGES_TOKEN }}
    ```

    A workflow's `GITHUB_TOKEN` can install only the packages that grant its repository read access, and Offload's packages belong to another account. Store a classic token with `read:packages` as a repository secret, `OFFLOAD_PACKAGES_TOKEN` in this example.

  </Step>
  <Step title="Install the packages">
    Install each Payload package under its upstream name, as an alias of its Offload build. Code keeps importing `payload` and `@payloadcms/*`.

    ```json package.json
    "dependencies": {
      "@adirishi/offload-cloudflare": "{{version}}",
      "@payloadcms/db-d1-sqlite": "npm:@adirishi/offload-db-d1-sqlite@{{version}}",
      "@payloadcms/richtext-lexical": "npm:@adirishi/offload-richtext-lexical@{{version}}",
      "@payloadcms/storage-r2": "npm:@adirishi/offload-storage-r2@{{version}}",
      "@payloadcms/tanstack-start": "npm:@adirishi/offload-tanstack-start@{{version}}",
      "@payloadcms/ui": "npm:@adirishi/offload-ui@{{version}}",
      "@tanstack/react-router": "^1.170.0",
      "@tanstack/react-start": "^1.169.1",
      "graphql": "^16.11.0",
      "payload": "npm:@adirishi/offload-payload@{{version}}",
      "react": "^19.3.0",
      "react-dom": "^19.3.0"
    },
    "devDependencies": {
      "@cloudflare/vite-plugin": "^1.64.0",
      "@vitejs/plugin-react": "^6.0.0",
      "@vitejs/plugin-rsc": "^0.5.21",
      "vite": "^8.0.0",
      "wrangler": "^4.151.0"
    }
    ```

    Every Payload package in the site must be an Offload build at the same version, including plugins you add later. For example, install `@payloadcms/plugin-seo` as `npm:@adirishi/offload-plugin-seo@{{version}}`. Payload's dev server throws when its packages' versions differ, and an upstream plugin would install its own upstream copy of `@payloadcms/ui`. `offloadVite()` checks this when Vite starts and when it builds, and its error gives the line to install.

    With pnpm 11, exclude Offload from the minimum release age, so a release installs on the day it's published. Allow the install scripts of `workerd` and `esbuild` too:

    ```yaml pnpm-workspace.yaml
    allowBuilds:
      esbuild: true
      workerd: true
    minimumReleaseAgeExclude:
      - "@adirishi/*"
    ```

  </Step>
  <Step title="Configure Vite">
    `offloadVite()` builds the site for workerd and runs `vite dev` in Node:

    ```ts vite.config.ts
    import { offloadVite } from "@adirishi/offload-cloudflare/vite";
    import path from "node:path";
    import { defineConfig } from "vite";

    export default defineConfig(
      offloadVite({
        payloadConfigPath: path.resolve(import.meta.dirname, "src/payload.config.ts"),
      }),
    );
    ```

    Map `@payload-config` to the same file in `tsconfig.json`, under `compilerOptions.paths`:

    ```json tsconfig.json
    "paths": { "@payload-config": ["./src/payload.config.ts"] }
    ```

  </Step>
  <Step title="Configure Wrangler">
    Bind a D1 database and an R2 bucket. The Cron Trigger runs Payload's jobs, including scheduled publishing.

    ```jsonc wrangler.jsonc
    {
      "name": "my-site",
      "main": "src/server.ts",
      "compatibility_date": "2026-10-01",
      "compatibility_flags": ["nodejs_compat"],
      "triggers": { "crons": ["*/5 * * * *"] },
      "d1_databases": [{ "binding": "D1", "database_name": "my-site", "database_id": "local" }],
      "r2_buckets": [{ "binding": "R2", "bucket_name": "my-site" }]
    }
    ```

    Put Payload's secret in `.dev.vars`, which Wrangler reads for local runs. Keep this file out of git.

    ```ini .dev.vars
    PAYLOAD_SECRET=a-long-random-string
    ```

    Run `pnpm wrangler types` to generate the `Env` type for these bindings.

  </Step>
  <Step title="Write the Payload config">
    `getBindings()` returns the Worker's bindings. In workerd they come from the runtime. In Node, for `vite dev` and the Payload CLI, they come from Wrangler's local state.

    ```ts src/payload.config.ts
    import { getBindings } from "@adirishi/offload-cloudflare";
    import { sqliteD1Adapter } from "@payloadcms/db-d1-sqlite";
    import { lexicalEditor } from "@payloadcms/richtext-lexical";
    import { r2Storage } from "@payloadcms/storage-r2";
    import path from "node:path";
    import { fileURLToPath } from "node:url";
    import { buildConfig } from "payload";

    const dirname = path.dirname(fileURLToPath(import.meta.url));
    const env = await getBindings();

    export default buildConfig({
      admin: { importMap: { baseDir: dirname } },
      collections: [
        { slug: "users", auth: true, fields: [] },
        { slug: "media", upload: true, fields: [] },
      ],
      db: sqliteD1Adapter({
        binding: env.D1,
        migrationDir: path.resolve(dirname, "migrations"),
        push: false,
      }),
      editor: lexicalEditor(),
      secret: env.PAYLOAD_SECRET,
      storage: [r2Storage({ bucket: env.R2, collections: { media: true } })],
    });
    ```

  </Step>
  <Step title="Add the routes">
    Payload's TanStack Start adapter keeps the site's routes in `src/app`. Copy these files from `e2e`:

    - `src/router.tsx` and `src/app/__root.tsx`, which pass Payload's search-param handling and root wrapper to TanStack Router
    - `src/app/_payload.tsx` and the `src/app/_payload/` directory, which hold the admin, REST, and server-function routes from Payload's TanStack Start template, plus `api.graphql.ts` for GraphQL

    Then run `pnpm payload generate:importmap` to rebuild `src/app/_payload/importMap.js` for your config. Your own pages go next to `_payload`, as `e2e` does in `src/app/_frontend`.

  </Step>
  <Step title="Export the Worker">
    `createPayloadWorker()` serves requests through TanStack Start and runs Payload's jobs on each Cron Trigger:

    ```ts src/server.ts
    import { createPayloadWorker } from "@adirishi/offload-cloudflare/worker";
    import config from "@payload-config";
    import handler from "@tanstack/react-start/server-entry";

    export default createPayloadWorker({ config, handler });
    ```

  </Step>
  <Step title="Create the schema and start the site">
    Generate the first migration, apply it to the local D1 database, and start the dev server:

    ```bash
    pnpm payload migrate:create
    pnpm payload migrate
    pnpm vite dev
    ```

    Open `/admin` on the address that Vite prints. Payload asks you to create the first user. After you create it, you see the dashboard with the **Users** and **Media** collections.

    This user is for local work only. `vite dev` runs in Node, which hashes the password with 600,000 PBKDF2 iterations, and a deployed Worker can verify at most 100,000. Create the users of the deployed site on the deployed Worker, as [Deploy to Cloudflare](/deploy) shows.

  </Step>
  <Step title="Run the Worker build">
    `vite dev` runs in Node. To run the bundle that Cloudflare runs, build it and serve it in local workerd:

    ```bash
    pnpm vite build
    pnpm vite preview
    ```

    The preview uses the same local D1 and R2 state as `vite dev`, so the user you created can log in. Local workerd doesn't enforce the deployed Worker's PBKDF2 limit, so this login doesn't show whether a deployed Worker accepts the password hash.

    The preview runs the last build, with the secrets that `vite build` copied from `.dev.vars` into it. After you change `.dev.vars`, build again before you preview.

  </Step>
</Steps>

## Set up your coding agent

`@adirishi/offload-cloudflare` ships an agent skill that explains what Offload changes about Payload, and points to the skill that the `payload` package ships for everything else. Add this line to the site's `AGENTS.md`:

```md AGENTS.md
For Payload work in this site, read `node_modules/@adirishi/offload-cloudflare/skills/offload/SKILL.md` first.
```

pnpm 12.11 and later can also link the skills that dependencies ship into the agent skill directories a project has, such as `.claude/skills`. After an install, pnpm lists `@adirishi/offload-cloudflare` and `@adirishi/offload-payload` as awaiting approval. Run `pnpm approve` and approve both. The first links Offload's `offload` skill, and the second links Payload's `payload` skill, which the Offload skill builds on. pnpm records the approval in `pnpm-workspace.yaml`, and each link points at the installed version, so the skills change when you update Offload.

Keep the `AGENTS.md` line too. It works with every package manager and agent, and it makes the agent read Offload's skill before Payload's, whose Next.js advice Offload's skill overrides.
