# e2e

`e2e` is a Payload site on Cloudflare Workers that Playwright drives. It is a separate pnpm project with its own pinned versions, because it installs Offload from a registry the way a site in its own repository does.

- For Payload work in this site, read `node_modules/@adirishi/offload-cloudflare/skills/offload/SKILL.md` first.
- `pnpm release e2e` from the repository root publishes the working tree and installs it here. After that, `pnpm test` in this directory reruns the suite against the installed release, and `CLOUDFLARE_ENV=postgres pnpm test` runs it on Postgres.
- The root `pnpm check` skips this directory's lint and type checks, because they need the installed release. `pnpm release e2e` runs `pnpm typecheck` and `pnpm lint` here, and you can run them yourself after an install. `.oxlintrc.json` extends the root config.
- The suite covers what Offload changes or depends on, plus the main editor flows. Payload's own test suite covers Payload's features.
- Each database has exactly one migration, `src/migrations/{d1,postgres}/*_initial.ts`, because every local run starts from an empty database. A schema change rewrites that migration in place and adds no migration files. Payload skips a migration whose name a database has already recorded, so `pnpm deploy:staging` drops every table in the staging D1 database with `migrate:fresh` before it deploys. Staging holds only test data.
  - After a schema change, run `pnpm migrations:regenerate`. For each database, `scripts/migrations.ts` generates the whole schema in a temporary directory, as `payload migrate:create initial` does in an empty migrations directory, and writes it over the committed `_initial.ts`. `migrate:create` doesn't connect to the database, so Postgres needs no Docker.
  - `pnpm migrations:check` generates the same migrations and fails with a diff when a committed one differs, or when a migrations directory holds another migration. `pnpm release e2e` runs it after lint.
  - Don't run `pnpm payload migrate:create` here. It diffs the schema against the newest drizzle-kit snapshot in the directory, and this repository keeps none, so it writes a second migration with the whole schema. `.gitignore` excludes the snapshots it writes.
- The `/api/e2e/*` endpoints exist only for the suite.
- To send a server function input that the site's components never send, call it with `callServerFn()` from `tests/fixtures.ts`. It posts to `/_serverFn/<id>` as TanStack Start's client does. In a production build, the ID is the SHA-256 of `<file>--<name>_createServerFn_handler`, with `<file>` relative to this directory. The input and the result are Seroval JSON, and the `sec-fetch-site: same-origin` header passes TanStack Start's CSRF check. `vite dev` uses other IDs, so the helper works only in the main suite.
- `src/components/form-builder/` and `src/components/payments/` come from Offload's shadcn registry, and `src/components/ui/` from shadcn's. After a change to `packages/form-builder/registry` or `packages/payments/registry`, format it, then reinstall the copies the way a site does: run `pnpm --filter @repo/docs registry` from the repository root, serve it with `python3 -m http.server 4880 -d ../docs/public`, then run `pnpm exec shadcn add @offload/form-builder-form @offload/newsletter-signup @offload/razorpay-checkout @offload/mips-payment-zone @offload/mips-confirm-order --overwrite` here. A test in each package fails while the copies differ from the registry.
- `stubs/razorpay.ts` and `stubs/mips.ts` stand in for the payment gateways on ports 4890 and 4891. Playwright starts them with the credentials in `.dev.vars.example`, which the Worker uses too. They implement each gateway's API, signing and callbacks, plus test-only routes under `/__stub/` that pay an order and return each webhook or IMN exactly as sent. Nothing in `src/` imports them, so the Worker never bundles them.
- Payment tests check out as guests through the plugin's REST endpoints or the shop pages under `src/app/_frontend/_shop`. Reconciliation settles every pending payment it finds, so only `tests/settlement.spec.ts` queues it, and its tests run one at a time.
